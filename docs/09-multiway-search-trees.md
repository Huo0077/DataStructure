## 9.1 存储墙与磁盘 I/O：为什么二叉树在海量数据面前失效？

在内存中，CPU 访问指针引用的耗时仅为几十纳秒；但在企业级数据库中，数据量通常高达数十 GB 到数十 TB，**远超物理内存容量，必须持久化在磁盘或 SSD 上**。

### 磁盘与内存的“物理时间鸿沟”：
- **内存读取**：\(\approx 50 \sim 100 \text{ ns}\)
- **机械磁盘随机寻道**：\(\approx 5 \sim 10 \text{ ms}\)（**相差 10 万倍！**）
- **SSD 随机读取**：\(\approx 50 \sim 100 \mu\text{s}\)（依然相差千倍！）

若使用红黑树或 AVL 树管理 1000 万条记录：
- 树高 \(h \approx \log_2(10^7) \approx 24\) 层；
- 每次查找目标键，指针散落在不同磁盘页中，最坏需要执行 **24 次磁盘 I/O**！
- 耗时 \(24 \times 10 \text{ ms} = 0.24 \text{ 秒}\)！单次查询耗费近 1/4 秒，系统吞吐量彻底归零！

**破局之道：增大分支因子（Branching Factor / Fan-out），将“瘦高的二叉树”压扁为“极矮胖的多路树”！**

```text
【二叉树 (矮胖度 = 2)】                 【多路树 (分支度 = 1000)】
         o                                      [ k1 | k2 | ... | k999 ]
       /   \                                    /    │     │    \
      o     o                                 ...   ...   ...   ...
    h = 24 层，24 次 I/O                      h = 3 层，仅需 3 次 I/O！
```

## 9.2 B 树（B-Tree）：经典多路平衡搜索树

1970 年，Rudolf Bayer 和 Edward M. McCreight 发明了 B 树（B 意为 Balanced 或 Boeing）。

<a id="c09-9-2-1"></a>
### 9.2.1 m 阶 B 树的严格定义与容量平衡不变量

一棵 \(m\) 阶（\(m \ge 3\)）B 树必须满足以下不变量：
1. **每个节点至多拥有 \(m\) 棵子树，至多包含 \(m - 1\) 个关键字（Keys）**；
2. **根节点若非叶子，则至少拥有 2 棵子树（至少 1 个关键字）**；
3. **除根节点外的所有非叶子节点，至少拥有 \(\lceil m/2 \rceil\) 棵子树，至少包含 \(\lceil m/2 \rceil - 1\) 个关键字**；
4. **所有叶子节点必须位于绝对相同的深度（完美高度平衡！）**；
5. **关键字有序排列**：节点内的关键字满足 \(K_1 < K_2 < \dots < K_k\)，且各子树中的所有关键字均落在对应关键字所夹的开区间之内。

```text
一个 5 阶 B 树节点的标准物理布局 (最多 4 个 Key, 5 个子指针):
┌────┬────┬────┬────┬────┬────┬────┬────┬────┐
│ P0 │ K1 │ P1 │ K2 │ P2 │ K3 │ P3 │ K4 │ P4 │
└────┴────┴────┴────┴────┴────┴────┴────┴────┘
其中: P0 树中所有值 < K1; P1 树中所有值介于 (K1, K2); ...
```

<a id="c09-9-2-2"></a>
### 9.2.2 插入操作：节点满溢与中间键上提分裂（Split）

新关键字永远首先插入到**底层叶子节点**中：
1. 若插入后该节点的关键字数 \(\le m - 1\)，插入成功；
2. 若插入后该节点关键字数达到 \(m\)（**发生溢出 Overflow**），则必须执行**中间键上提分裂**：
   - 提取该节点正中间的关键字（位置在 \(\lfloor m/2 \rfloor\)）；
   - 将中间键**推入其父节点**中；
   - 原节点裂变为左右两个独立的子节点，中间键成为连接它们的父级枢纽；
   - 若父节点也因吸收新键而溢出，则递归向上分裂，直至根节点；若根节点也分裂，则树高增 1！

```text
示例：在 3 阶 B 树 (2-3 树) 中插入 15
原节点: [ 10 | 20 ] (已满)
插入 15 后临时状态: [ 10 | 15 | 20 ] (溢出!)
中间键 15 向上提升:
                  [ 15 ] (新父节点)
                 /      \
             [ 10 ]    [ 20 ]
```

<a id="c09-9-2-3"></a>
### 9.2.3 删除操作：借位（Borrow）与下溢合并（Merge）

若被删除关键字在非叶子节点中，**必须用其前驱或后继关键字覆盖**，将删除操作转化为底层叶子节点的删除。

若删除后叶子节点的关键字数 \(< \lceil m/2 \rceil - 1\)（**发生下溢 Underflow**）：
- **分支 A（向富裕兄弟借位）**：  
  若左或右相邻兄弟拥有多于下限的关键字，不能直接借过来，必须**通过父节点进行“三方轮换借位”**（父节点的键下沉，兄弟节点的键上浮到父节点）。
- **分支 B（向贫困兄弟合并）**：  
  若左右兄弟均无富余，则将当前节点、相邻兄弟节点以及父节点中介于它们之间的关键字**三者合并为一个新节点**。父节点因此失去一个键，若父节点也下溢，递归向上调整！

<a id="c09-9-3"></a>
## 9.3 B+ 树（B+ Tree）：数据库与文件系统的索引霸主

尽管 B 树大幅降低了树高，但它在数据库查询中依然面临一个致命短板：**范围查询性能低下**。B+ 树正是为了解决这一痛点而诞生的终极形态。

<a id="c09-9-3-1"></a>
### 9.3.1 B+ 树相对 B 树的架构革新

```text
【B 树】所有节点均存储完整的 Key + Data
               [ 20(Data) ]
              /            \
    [ 10(Data) ]          [ 30(Data) ]

【B+ 树】非叶子仅存 Key (做路由导航)，所有 Data 集中于叶子，叶子由双向链表相连
                   [ 20 ] (仅为路由索引)
                  /      \
      [ 10, Data ] <====> [ 20, Data ] <====> [ 30, Data ]  (底层双向链表!)
```

<a id="c09-9-3-2"></a>
### 9.3.2 为什么 MySQL InnoDB 坚定选择 B+ 树？（四大决定性理由）

1. **磁盘 I/O 效率达到物理极限（树极度矮胖）**：  
   InnoDB 的默认物理页大小为 16 KB。若为主键索引（`bigint` 占 8B，子指针占 6B，单条路由占 14B），一个 16KB 的内部节点可容纳 \(16384 / 14 \approx 1170\) 个分支指针！  
   - 深度为 3 的 B+ 树可容纳：\(1170 \times 1170 \times 16 \approx 2000 \text{ 万行数据}\)！  
   - **千万级的数据表，只需 3 次磁盘 I/O 即可精确定位！根节点常驻内存，实际仅需 1~2 次 I/O！**
2. **范围查询极速吞吐（Range Query）**：  
   执行 `WHERE age BETWEEN 18 AND 30` 时，B 树必须执行复杂的中序遍历跨页跳转；而 B+ 树**只需通过索引找到 18，然后沿着底层双向链表顺序线性扫描至 30**，顺序 I/O 吞吐量极高！
3. **查询性能高度稳定**：  
   任何查询都必须一路走到叶子节点，查询耗时高度一致（无抖动）。
4. **叶子节点可直接存放整行数据（聚集索引）**：  
   减少一次回表查询开销。

<a id="c09-9-3-3"></a>
### 9.3.3 叶节点分裂与中间键“保留副本”的关键机制

> ⚠️ **B+ 树与 B 树最核心的代码区别**：  
> - B 树分裂时，中间键被**抽走并推入父节点**（原节点不再包含该键）；  
> - B+ 树分裂时，中间键**被推入父节点作为路由副本，但该键同时必须完好保留在右侧叶子节点中**！因为所有真实数据必须在底层叶子中全集呈现！

## 9.4 工业级数据库实战：聚集索引与二级索引的物理组织

在 MySQL InnoDB 存储引擎中：
- **聚集索引（Clustered Index）**：以主键构建的 B+ 树，其**叶子节点直接存储整行数据记录**；
- **二级索引（Secondary Index / 辅助索引）**：以非主键列（如 `email`）构建的 B+ 树，其**叶子节点存储的是该列的值以及对应的主键值**；
- **回表（Bookmark Lookup）**：通过二级索引查到主键后，再次进入聚集索引 B+ 树查找完整行数据的过程。

## 本章小结

1. **外存瓶颈重塑算法体系**：算法分析从“比较次数最少”演进为“磁盘页读取次数最少”。
2. **B 树的分支哲学**：通过多路平衡保证完美树高，中间键上提与向兄弟借位是维持容量不变量的核心。
3. **B+ 树的解耦艺术**：将索引路由（非叶子）与数据存储（叶子）彻底分离，底层双向链表化解了范围查询的世纪难题。
4. **数据库索引的基石**：B+ 树以 3~4 层的极浅深度统领千万级数据，是当代所有关系型数据库的底层核心支柱。

## 思考题与经典大厂面试题

1. **InnoDB 为什么不用哈希表或红黑树做索引？**：分别从范围查询、磁盘页局部性、树高与内存利用率角度给出系统性对比。
2. **B+ 树并发控制（B-Tree Latching）**：在多线程高并发读写环境下，B+ 树分裂可能向上层传播引起连锁加锁。工业界如何利用“蟹行锁（Crabbing / Lock Coupling）”或“乐观锁并发”来保证高效读写？
3. **手算演练**：给定一棵空的 3 阶 B+ 树，依次插入数据 `[5, 15, 25, 35, 45]`，请画出每次分裂后的整棵树形态，特别标明叶子链表的链接关系。
